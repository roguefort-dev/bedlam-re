## Fixed: visible mission pointer did not drive canonical click position

[code inspection + regression + live verification, high confidence]
`ShellApp::run_pumps` aligned only the menu cursor with the window pointer.
Mission input instead integrated physical window deltas into canonical game
coordinates. The cursor was also freshly initialized on mission entry and
could disagree with a stationary visible pointer. Scaling, entry and refocus
therefore allowed clicks to target somewhere other than the visible control.

The shell now uses the active mission's current cursor when producing the same
canonical relative InputFrame that the mission already consumes. Scene input
and simulation semantics are unchanged. Existing Fill-mode relative fallback
is unchanged and remains a separate scaling limitation.

Regression `visible_map_button_click_reaches_mission_at_scaled_resolutions`
traverses scenes with mouse edges, loads the real ZONEA corpus, maps the visible
MAP-button position at 1200x900 and 1920x1080, and asserts both canonical cursor
position and map-overlay activation. It failed before the fix: actual cursor
(320,240), expected (560,450). It passes after the fix.

Live verification: rebuilt windowed shell, boot/menu, New Game, two clicks
through the pending blank scenes, then clicked MAP at its visible position.
The strategic-map overlay appeared. This is a control verification, not a
completed mission or a claim of original map-rendering parity.
